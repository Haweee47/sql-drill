제출 전 체크

  • 출력 컬럼 이름과 순서가 문제와 똑같은가
  • ORDER BY 를 넣었는가 (빠지면 로직이 맞아도 0점)
  • ROUND 자릿수가 문제와 같은가
  • LEFT JOIN 인가 INNER 인가 — 빠지는 행이 없는가
  • 나눗셈에 100.0 또는 1.0 을 섞었는가
  • 분모가 0 이 될 수 있으면 NULLIF 를 썼는가
  • 조인으로 행이 불어나 COUNT 가 부풀지 않는가 (DISTINCT)
  • 빈 그룹·NULL·동점에서도 답이 맞는가

실수 포인트
  • ORDER BY 가 없으면 의미가 없다. MySQL 은 에러를 내지 않고 아무 순서나 쓰므로 결과가 들쭉날쭉해진다. 반드시 넣는다.

  • default 를 0 으로 주면 증감 계산에서 첫 행이 전체 증가로 잡힌다. 보통은 NULL 로 두는 게 맞다.

  • offset 에 컬럼을 넣을 수 없다. 상수만 된다.

SELECT nm, score,
  ROW_NUMBER() OVER (ORDER BY score DESC) AS row_num,
  RANK()       OVER (ORDER BY score DESC) AS rnk,
  DENSE_RANK() OVER (ORDER BY score DESC) AS dense,
  NTILE(2)     OVER (ORDER BY score DESC) AS 절반,
  ROUND(PERCENT_RANK() OVER (ORDER BY score DESC),2) AS pct,
  ROUND(CUME_DIST()    OVER (ORDER BY score DESC),2) AS cume
FROM (SELECT 'A' AS nm, 90 AS score UNION ALL SELECT 'B',80
      UNION ALL SELECT 'C',80 UNION ALL SELECT 'D',70) t
ORDER BY score DESC, nm

실수 포인트
  • 동점 처리가 전부 다르다. ROW_NUMBER 1,2,3,4 / RANK 1,2,2,4 / DENSE_RANK 1,2,2,3.
  • “1등 한 명만” → ROW_NUMBER = 1. “공동 1등 전부” → RANK = 1.
  • ROW_NUMBER 는 동점일 때 누가 먼저일지 보장되지 않는다. 재현성이 필요하면 ORDER BY score DESC, id 처럼 타이브레이커를 넣는다.
  • WHERE 에서 쓸 수 없다. 서브쿼리로 감싸고 바깥 WHERE 에서 거른다.
  • NTILE(n) 의 n 은 상수. 행이 n 으로 안 나뉘면 앞쪽 묶음이 1개씩 더 가진다.
  • PERCENT_RANK = (rank−1)/(행수−1), 0 부터 시작. CUME_DIST = 나 이하 비율, 0 보다 크고 1 이하.

COALESCE(a,b,...)  ·  NULLIF(a,b)  ·  IFNULL(a,b)  ·  x IS [NOT] NULL
인자설명생략하면
COALESCE(a,b,c,…)앞에서부터 처음 만나는 NULL 아닌 값. 인자 수 제한 없음. 표준 SQL — 어느 DB 에서나 된다. 이것만 쓰면 된다.
NULLIF(a,b)a 와 b 가 같으면 NULL, 다르면 a. 이름이 헷갈리지만 'a 가 b 면 NULL 로 만들어라' 는 뜻이다. 0 나누기 방어 전용.
IFNULL(a,b)COALESCE 의 2인자 버전. MySQL·SQLite 전용. PostgreSQL·MS SQL 에 없다. 쓸 이유가 없다.
NVL / ISNULLNVL 은 Oracle 전용. ISNULL 은 MS SQL 에서는 ISNULL(a,b) 2인자 대체, MySQL 에서는 ISNULL(x) 1인자 참/거짓 — 이름만 같고 다른 함수다. 둘 다 쓰지 마라.
x IS NULL / IS NOT NULLNULL 판정은 이것뿐이다. x = NULL 은 참이 아니라 NULL 이라 WHERE 에서 항상 걸러진다.

       COUNT(x)  AS cnt_col,    -- 0
       SUM(x)    AS sum_x,      -- NULL  ← 0 이 아니다
       AVG(x)    AS avg_x,      -- NULL

SELECT AVG(x)                  AS avg_x,
       SUM(x) * 1.0 / COUNT(*) AS sum_over_rows,
       COUNT(x)                AS non_null_cnt
FROM t;

SELECT 5 WHERE 5 NOT IN (1, 2, NULL);   -- 0행
SELECT 5 WHERE 5 IN (5, NULL);          -- 1행 (IN 은 괜찮다)

실수 포인트
  • 철자를 틀리면 그냥 문법 오류다. C-O-A-L-E-S-C-E. COALECSE, COALEASE, COALSCE 다 틀린 철자다. 시험장에서 빨간 줄이 안 뜨니 눈으로 확인해야 한다.
  • 집계 함수의 빈 입력 반환값 — 이게 가장 자주 틀리는 부분이다.
    COUNT 는 0, SUM·AVG·MAX·MIN 은 NULL. 그래서 LEFT JOIN 뒤에 금액을 0 으로 보이고 싶으면 COALESCE(SUM(amount), 0) 이 필요하다. COALESCE 를 SUM 안에 넣을지 밖에 씌울지는 '그룹이 빌 수 있는가' 로 갈린다.
    LEFT JOIN + GROUP BY 왼쪽테이블 이면 그룹마다 최소 한 행(NULL 행)이 남으므로 SUM(COALESCE(amount,0)) 도 0 이 나온다.
    하지만 그룹 자체가 비는 경우 — 상관 서브쿼리 (SELECT SUM(amount) FROM payments WHERE user_id=u.user_id) 나 INNER JOIN 뒤 — 는 행이 0개라 SUM 이 NULL 이고 안쪽 COALESCE 는 실행될 기회조차 없다.
    밖에 씌우는 쪽이 항상 안전하다: COALESCE(SUM(amount), 0).
  • AVG 는 NULL 을 분모에서도 뺀다. 값이 10, NULL, 20 이면 AVG 는 (10+20)/2 = 15 이지 (10+20)/3 = 10 이 아니다. '결제 안 한 사람을 0 으로 치고 평균' 을 원하면 AVG(COALESCE(amount, 0)) 처럼 먼저 채워야 한다. ARPU 와 ARPPU 가 갈리는 지점이 정확히 여기다.
  • NOT IN + NULL = 전멸. 서브쿼리 결과에 NULL 이 하나라도 섞이면 WHERE id NOT IN (SELECT ...) 가 0행을 돌려준다. 5 NOT IN (1,2,NULL) 은 '5≠1 AND 5≠2 AND 5≠NULL' 이고 마지막이 NULL 이라 전체가 NULL(거짓 취급)이 된다. NOT IN 대신 NOT EXISTS 나 LEFT JOIN … IS NULL 을 써라. IN 은 반대로 멀쩡하다 (하나만 맞으면 참).
    NOT EXISTS 는 NULL 에 면역이다. NOT EXISTS (SELECT 1 FROM p WHERE p.user_id = u.user_id) 에서 p.user_id 가 NULL 인 행은 비교가 NULL → 매칭 실패 → 자동으로 무시된다. IS NOT NULL 을 따로 안 써도 맞는 답이 나온다. 그래서 '존재하지 않는 것 찾기' 는 NOT EXISTS 를 기본값으로 삼아라.
  • 정렬에서 NULL 의 위치 — 엔진마다 다르다. 실제로 돌려 본 결과:
    MySQL·SQLite : NULL 을 가장 작은 값으로 본다 → ASC 면 맨 앞, DESC 면 맨 뒤
    PostgreSQL·DuckDB : 기본이 NULLS LAST → ASC 에서도 맨 뒤
    그래서 정렬 컬럼에 NULL 이 있을 수 있으면 직접 정해 줘라: ORDER BY (금액 IS NULL), 금액 DESC — IS NULL 은 0/1 이라 이걸 첫 키로 쓰면 NULL 을 뒤로 밀 수 있다. MySQL 의 ORDER BY 금액 IS NULL, 금액 도 같은 뜻이다 (NULLS LAST 문법은 MySQL 에 없다).
  • 타입 승격 함정 — 형님이 말한 '데이터 타입 문제' 가 이것이다. COALESCE 의 반환 타입은 인자들의 공통 타입이다. COALESCE(금액, '없음') 처럼 숫자에 문자를 섞으면 컬럼 전체가 문자열이 되고, 그 뒤 정렬이 사전순으로 깨진다 ('9' > '20'). MySQL·SQLite 는 이 변환을 오류 없이 조용히 하고, PostgreSQL·DuckDB 는 오류를 낸다. 해결: 보여 주는 값과 정렬하는 값을 분리해서 SELECT COALESCE(CAST(금액 AS CHAR), '없음') … ORDER BY (금액 IS NULL), 금액.
  • 0 과 NULL 은 다른 뜻이다. 0 은 '거래했고 금액이 0', NULL 은 '거래 기록이 없음' 이다. LEFT JOIN 뒤에 어느 쪽으로 채울지는 비즈니스 판단이고, 문제에 명시돼 있다. A/B 테스트의 분모처럼 '참가했지만 행동 안 함' 을 0 으로 세야 하는 경우가 많으니 문제를 다시 읽어라.
  • 0 으로 나눈 결과도 엔진마다 다르다. 실측: SQLite·MySQL → NULL, DuckDB → inf, PostgreSQL·MS SQL → 오류. 즉 시험 환경에서는 NULLIF 없이도 NULL 이 나와 통과할 수 있지만, 습관을 안 들이면 다른 환경에서 쿼리가 터진다.
  • NULL 은 GROUP BY 에서 하나의 그룹이 되고, COUNT(DISTINCT) 에서는 안 세어진다. GROUP BY channel 에 channel 이 NULL 인 행들은 모여서 NULL 그룹 한 줄이 된다. 반면 COUNT(DISTINCT x) 는 NULL 을 빼고 센다 (NULL, NULL, 1 → 1).
  • 문자열 연결에 NULL 이 끼면 전체가 NULL 이다. 'a' || NULL → NULL. MySQL CONCAT 도 같다. CONCAT_WS 는 NULL 을 건너뛴다. 이름 조합 같은 걸 만들 때 COALESCE(미들네임, '') 로 먼저 채워라.
  • NULLIF 와 IFNULL 을 바꿔 쓰면 정반대가 된다. NULLIF(분모, 0) 은 0 을 NULL 로 만들어 나눗셈을 방어하고, IFNULL(분모, 0) 은 NULL 을 0 으로 만들어 0 나누기를 일부러 만든다.

이렇게 푼다

  1. 먼저 사람마다 첫 결제일이 언제인지 따로 구해 둔다.
  2. 유저 명단 왼쪽에 두고 그 첫 결제일을 옆에 붙인다 (LEFT JOIN).
  3. 가입한 달로 묶어서, 전체 인원을 세고 / 30일 안에 결제한 사람만 따로 센다.
  4. 나누고 ×100, 소수점 둘째 자리까지.

이것만 피하면 된다

  • 그냥 JOIN 으로 붙이면 안 된다. 결제 안 한 사람이 통째로 사라져서 분모가 줄어들고, 전환율이 실제보다 훨씬 높게 나온다. LEFT JOIN — '왼쪽 명단은 무조건 다 남긴다' 는 뜻이다.
  • 100 이 아니라 100.0. 정수끼리 나누면 소수점이 날아가서 0 이 나오는 환경이 있다.
자세한 설명
묻는 것 · ‘전체’가 분모인 비율을 구할 줄 아는가. 그리고 조건부 집계.

풀이 순서

  1. 유저별 첫 결제일을 먼저 만든다 (MIN). payments 를 바로 조인하면 한 유저가 여러 행이 된다.
  2. users 를 기준으로 LEFT JOIN. 결제 없는 유저가 분모에 남아야 한다.
  3. converted 는 조건부 집계로 센다.
  4. 비율은 converted / signups × 100.

정답 (MySQL)

WITH first_pay AS (
  SELECT user_id, MIN(paid_date) AS fp FROM payments GROUP BY user_id
)
SELECT DATE_FORMAT(u.signup_date, '%Y-%m') AS signup_month,
       COUNT(*) AS signups,
       SUM(CASE WHEN f.fp <= DATE_ADD(u.signup_date, INTERVAL 30 DAY)
                THEN 1 ELSE 0 END) AS converted,
       ROUND(100.0 * SUM(CASE WHEN f.fp <= DATE_ADD(u.signup_date, INTERVAL 30 DAY)
                THEN 1 ELSE 0 END) / COUNT(*), 2) AS conversion_rate
FROM users u
LEFT JOIN first_pay f ON f.user_id = u.user_id
GROUP BY signup_month
ORDER BY signup_month;

함정

  • INNER JOIN 을 쓰면 결제 없는 유저가 사라져 전환율이 부풀려진다. 이 문제의 핵심 함정.
  • 분자를 전체 결제자로 쓰기 쉽다. 30일 조건이 붙은 쪽이어야 한다.
  • ×100 누락. *1.0 만으로는 비율(0.23)이지 퍼센트가 아니다.
  • f.fp IS NOT NULL 은 안 써도 된다. NULL 과의 비교는 NULL 이라 CASE 가 거짓으로 떨어진다.

이렇게 변형된다

“가입 후 7일 이내 재방문율”, “첫 구매까지 N일 이내 비율” — 날짜 기준만 바뀐다.

Q2. 채널별 퍼널 전환율쉬움

쉬운 설명

놀이기구 줄. 입구에 100명 → 중간에 60명 → 실제로 탄 사람 20명. 각 지점에 몇 명 남았나를 세는 것.

단계사람 수
view_landing (들어옴)1,000
signup_done (가입 완료)620
first_payment (첫 결제)180

최종 전환율 = 180 / 1,000 × 100 = 18.00

이렇게 푼다

  1. 단계마다 '그 행동을 한 사람 수' 를 센다.
  2. 채널별로 묶는다.
  3. 마지막 단계 ÷ 첫 단계 × 100.

이것만 피하면 된다

  • 사람 수로 세야 한다. 같은 사람이 같은 행동을 여러 번 기록에 남기기 때문이다. 기록 개수를 세면 숫자가 부풀어 오른다. → 중복을 지우고 센다 (DISTINCT).
자세한 설명
묻는 것 · 세로로 쌓인 이벤트를 가로 단계로 펼칠 줄 아는가.

풀이 순서

  1. 단계별로 COUNT(DISTINCT CASE WHEN ... THEN user_id END).
  2. 같은 유저가 같은 이벤트를 여러 번 남길 수 있으므로 DISTINCT 필수.
  3. 최종 전환율은 마지막 단계 ÷ 첫 단계.

정답 (MySQL)

SELECT channel,
       COUNT(DISTINCT CASE WHEN event_name='view_landing'  THEN user_id END) AS landing_users,
       COUNT(DISTINCT CASE WHEN event_name='signup_done'   THEN user_id END) AS signup_users,
       COUNT(DISTINCT CASE WHEN event_name='first_payment' THEN user_id END) AS paid_users,
       ROUND(100.0 * COUNT(DISTINCT CASE WHEN event_name='first_payment' THEN user_id END)
             / NULLIF(COUNT(DISTINCT CASE WHEN event_name='view_landing' THEN user_id END), 0), 2)
         AS final_cvr
FROM events
GROUP BY channel
ORDER BY final_cvr DESC;

함정

  • DISTINCT 누락 — 중복 이벤트가 있으면 단계 인원이 부풀려진다.
  • COUNT(CASE WHEN ...) 는 0 이 아니라 NULL 을 세지 않는 것이다. ELSE 를 쓰지 말 것. ELSE 0 을 넣으면 전부 세어진다.
  • 첫 단계가 0 인 채널이 있으면 0 나누기. NULLIF 로 막는다.

이렇게 변형된다

“단계 간 전환율”(2→3, 3→4)로 바뀌면 분모를 직전 단계로 바꾸면 된다.

Q3. 월별 매출 · 누적 · 전월 대비보통

쉬운 설명

용돈 기록장. 이번 달 얼마 썼나 / 지금까지 합쳐서 얼마 / 지난달보다 얼마나 늘었나.

월이번 달누적전월 대비
1월100100(없음)
2월150250+50.00%
3월120370-20.00%

누적은 '위 칸들을 다 더한 값'. 전월 대비는 '한 칸 위 값과 비교'.

이렇게 푼다

  1. 월별 결제 금액 합계를 먼저 만든다.
  2. 누적은 처음부터 이번 줄까지 더하기 — SUM(매출) OVER (ORDER BY 월).
  3. 지난달 값은 한 칸 위에서 끌어온다 — LAG(매출) OVER (ORDER BY 월).
  4. (이번 − 지난) ÷ 지난 × 100.

이것만 피하면 된다

  • 첫 달은 전월 대비가 NULL 이다. 비교할 지난달이 없으니까. 0 으로 채우면 '증감 없음' 이라는 다른 뜻이 된다.
  • 누적을 구할 때 OVER (ORDER BY 월) 에서 ORDER BY 를 빼면 전체 합계가 모든 줄에 똑같이 들어간다.
자세한 설명
묻는 것 · 윈도우 함수 기본기. 누적과 LAG.

풀이 순서

  1. 월 단위로 먼저 집계해 한 달 = 한 행으로 만든다.
  2. 그 위에서 SUM() OVER (ORDER BY) 로 누적.
  3. LAG() 로 전월 값을 끌어와 증감률.

정답 (MySQL)

WITH m AS (
  SELECT DATE_FORMAT(paid_date, '%Y-%m-01') AS mm, SUM(amount) AS rev
  FROM payments GROUP BY mm
)
SELECT DATE_FORMAT(mm, '%Y-%m') AS month,
       rev AS revenue,
       SUM(rev) OVER (ORDER BY mm) AS cumulative_revenue,
       ROUND(100.0 * (rev - LAG(rev) OVER (ORDER BY mm))
             / LAG(rev) OVER (ORDER BY mm), 2) AS mom_growth
FROM m
ORDER BY mm;

함정

  • 집계 전에 윈도우를 쓰려 하면 안 된다. GROUP BY 로 월별 한 행을 먼저 만들고 그 위에서 윈도우.
  • 정렬용으로 '%Y-%m-01'(월 첫날)을 쓰고 출력은 '%Y-%m'. 문자열 '2026-1' 로 정렬하면 10월이 1월 뒤에 온다.
  • 첫 달 증감률은 NULL 이 맞다. 0 으로 채우지 말 것.
  • MySQL 은 LAG(rev) 를 별칭으로 재사용할 수 없다. 두 번 풀어 쓴다.

이렇게 변형된다

“전년 동월 대비”면 LAG(rev, 12).

Q4. 가입 코호트별 월간 리텐션어려움

쉬운 설명

3월에 입학한 애들이 1달 뒤·2달 뒤에 몇 명 남았나. 입학한 달마다 따로 추적한다. 반이 다르면 섞지 않는다.

가입 월0개월1개월2개월
1월 (100명)100%42%28%
2월 (120명)100%38%25%

가로가 '가입 후 몇 달째', 세로가 '언제 가입한 묶음'. 분모는 그 줄의 전체 인원이고 끝까지 안 바뀐다.

이렇게 푼다

  1. 사람마다 가입한 달을 붙인다. 이게 그 사람이 속한 '묶음' 이다.
  2. 접속 기록마다 가입 후 몇 달째인가를 계산한다 (접속한 달 − 가입한 달).
  3. 가입한 달 × 경과 개월로 묶어서 사람 수를 센다.
  4. 그 수를 그 묶음의 전체 인원으로 나눈다.

이것만 피하면 된다

  • 분모는 접속 기록에서 세면 안 된다. 가입한 사람 명단에서 세야 한다. 접속 기록에서 세면 '접속한 사람 중 접속한 사람' 이 되어 항상 100% 가 나온다.
  • 사람 수는 중복을 지우고 센다. 한 달에 열 번 접속한 사람은 한 명이다.
자세한 설명
묻는 것 · 코호트 분석의 뼈대. 분모 고정 + 경과 개월.

풀이 순서

  1. 코호트 = 가입 월. 유저마다 하나.
  2. 활동 = app_open 이 있는 월. 유저×월 중복 제거.
  3. TIMESTAMPDIFF(MONTH, 코호트, 활동월) 로 경과 개월 M+1, M+2…
  4. 분모는 코호트 전체 인원. 활동 안 한 사람도 포함.

정답 (MySQL)

WITH base AS (
  SELECT user_id, DATE_FORMAT(signup_date, '%Y-%m-01') AS cohort FROM users
),
act AS (
  SELECT DISTINCT user_id, DATE_FORMAT(event_date, '%Y-%m-01') AS m
  FROM events WHERE event_name = 'app_open'
)
SELECT DATE_FORMAT(b.cohort, '%Y-%m') AS cohort_month,
       COUNT(DISTINCT b.user_id) AS cohort_size,
       ROUND(100.0 * COUNT(DISTINCT CASE WHEN TIMESTAMPDIFF(MONTH, b.cohort, a.m)=1
             THEN b.user_id END) / COUNT(DISTINCT b.user_id), 1) AS m1_retention,
       ROUND(100.0 * COUNT(DISTINCT CASE WHEN TIMESTAMPDIFF(MONTH, b.cohort, a.m)=2
             THEN b.user_id END) / COUNT(DISTINCT b.user_id), 1) AS m2_retention,
       ROUND(100.0 * COUNT(DISTINCT CASE WHEN TIMESTAMPDIFF(MONTH, b.cohort, a.m)=3
             THEN b.user_id END) / COUNT(DISTINCT b.user_id), 1) AS m3_retention
FROM base b
LEFT JOIN act a ON a.user_id = b.user_id
GROUP BY cohort_month
ORDER BY cohort_month;

함정

  • INNER JOIN 금지. 한 번도 활동 안 한 유저가 분모에서 빠지면 리텐션이 과대평가된다.
  • 분모를 COUNT(*) 로 쓰면 안 된다. 조인으로 행이 불어나 있다. COUNT(DISTINCT user_id).
  • 활동 테이블에서 유저×월 중복 제거를 먼저 해야 한다. 안 하면 한 유저가 여러 번 세어질 수 있다 — DISTINCT 를 써서 막는다.
  • 아직 기간이 안 지난 코호트는 0 이 나온다. 정상이다.

이렇게 변형된다

주 단위면 TIMESTAMPDIFF(WEEK, ...). “결제 리텐션”이면 활동 테이블을 payments 로 바꾼다.

Q5. 월별 매출 분해 (신규/기존/복귀)어려움

쉬운 설명

이번 달 매출을 통 세 개에 나눠 담기 — 처음 온 손님 / 지난달에도 온 손님 / 오랜만에 다시 온 손님. 세 통을 합치면 전체와 딱 맞아야 한다.

이 사람이어느 통
태어나서 첫 결제가 이번 달신규
지난달에도 결제했음기존
전에 결제한 적 있는데 지난달엔 없음복귀

이 세 칸은 서로 겹치지 않고, 빠지는 경우도 없다. 그래서 합이 딱 맞는다.

이렇게 푼다

  1. 사람마다 생애 첫 결제가 몇 월인지를 구해 둔다.
  2. 결제 줄마다 그 사람의 직전 결제가 몇 월이었나를 한 칸 위에서 끌어온다.
  3. 위 표대로 셋 중 하나를 고른다 — CASE WHEN 첫결제월 = 이번달 THEN '신규' WHEN 직전결제월 = 지난달 THEN '기존' ELSE '복귀' END.
  4. 통별로 금액을 합친다.

이것만 피하면 된다

  • 조건 순서를 바꾸면 안 된다. CASE 는 위에서부터 보고 맞으면 멈춘다. 신규 → 기존 → 복귀 순서로 두면 자동으로 겹치지 않는다.
  • 검산하는 법: 세 통을 더해서 전체 매출과 같은지 본다. 안 맞으면 조건이 겹쳤거나 빠진 것이다. 제출 전에 꼭 해 봐라.
자세한 설명
묻는 것 · FP&A 의 핵심. 배타적 분류를 만들 줄 아는가.

풀이 순서

  1. 유저 × 월 단위로 먼저 집계한다. 이걸 안 하면 아래가 전부 꼬인다.
  2. MIN(m) OVER (PARTITION BY user_id) → 그 유저의 첫 결제 월.
  3. LAG(m) OVER (PARTITION BY user_id ORDER BY m) → 직전 결제 월.
  4. 첫 달이면 신규. 아니면 직전 달이 바로 전월인지로 기존/복귀를 가른다.

정답 (MySQL)

WITH mu AS (
  SELECT user_id, DATE_FORMAT(paid_date, '%Y-%m-01') AS m, SUM(amount) AS amt
  FROM payments GROUP BY user_id, m
),
l AS (
  SELECT user_id, m, amt,
         LAG(m) OVER (PARTITION BY user_id ORDER BY m) AS prev_m,
         MIN(m) OVER (PARTITION BY user_id)            AS first_m
  FROM mu
)
SELECT DATE_FORMAT(m, '%Y-%m') AS month,
       SUM(CASE WHEN m = first_m THEN amt ELSE 0 END) AS new_revenue,
       SUM(CASE WHEN m <> first_m AND prev_m = DATE_SUB(m, INTERVAL 1 MONTH)
                THEN amt ELSE 0 END) AS existing_revenue,
       SUM(CASE WHEN m <> first_m AND (prev_m IS NULL OR prev_m < DATE_SUB(m, INTERVAL 1 MONTH))
                THEN amt ELSE 0 END) AS returning_revenue,
       SUM(amt) AS total_revenue
FROM l
GROUP BY month
ORDER BY month;

함정

  • 분류 순서가 핵심. 첫 달(new)을 먼저 떼어내고, 나머지를 ‘직전 달 있음/없음’으로 가른다. 순서를 바꾸면 겹치거나 빈다.
  • 세 항목 합 = total 인지 반드시 검산한다. 틀리면 분류가 겹치거나 빈 것이다.
  • 유저×월 집계를 건너뛰고 payments 에 바로 LAG 를 걸면, 같은 달 두 번 결제한 유저에서 깨진다.
  • 날짜 문자열끼리 비교하므로 '%Y-%m-01' 형식을 일관되게 쓴다.

이렇게 변형된다

이탈(churn) 매출까지 요구하면, 직전 달에는 있었는데 이번 달에 없는 유저를 따로 만들어 음수로 붙인다.

Q6. 채널별 첫 결제까지 일수의 중앙값어려움

쉬운 설명

반 애들 키를 작은 순서로 줄 세우고 딱 가운데 애의 키. 평균이 아니다.

인원줄 세운 값중앙값
5명 (홀수)1 · 2 · 3 · 4 · 53번째 = 3
4명 (짝수)1 · 2 · 3 · 42·3번째 평균 = 2.5

홀수면 가운데 하나, 짝수면 가운데 둘의 평균. MySQL 에는 MEDIAN 함수가 없어서 직접 만들어야 한다.

이렇게 푼다

  1. 채널 안에서 값을 작은 순서로 번호를 매긴다 (1, 2, 3 …).
  2. 그 채널의 전체 인원 수도 같은 줄에 같이 붙여 둔다.
  3. 가운데 번호만 남긴다 — (인원+1)/2 와 (인원+2)/2 두 개를 소수점 버려서 쓴다.
  4. 남은 값의 평균을 낸다.

이것만 피하면 된다

  • 왜 번호 두 개냐: 5명이면 (5+1)/2=3, (5+2)/2=3(소수점 버림) → 둘 다 3번 → 한 개만 남는다. 4명이면 (4+1)/2=2, (4+2)/2=3 → 2번·3번 두 개가 남는다. 홀수·짝수를 따로 안 나누고 한 식으로 처리하는 요령이다.
  • 소수점 버림이 필요하다. 나눗셈이 소수로 나오는 환경에서는 FLOOR 를 꼭 씌워라.
자세한 설명
묻는 것 · MySQL 에 MEDIAN 이 없을 때 직접 만들 줄 아는가.

풀이 순서

  1. 유저별 첫 결제일 → 가입일과의 차이(일수).
  2. 채널 안에서 일수 오름차순으로 ROW_NUMBER(), 동시에 COUNT() OVER 로 인원수.
  3. 가운데 위치만 남긴다. 홀수면 1개, 짝수면 2개.
  4. 남은 값을 AVG 하면 짝수 평균까지 한 번에 처리된다.

정답 (MySQL)

WITH f AS (
  SELECT p.user_id, u.channel,
         DATEDIFF(MIN(p.paid_date), u.signup_date) AS d
  FROM payments p JOIN users u ON u.user_id = p.user_id
  GROUP BY p.user_id, u.channel, u.signup_date
),
r AS (
  SELECT channel, d,
         ROW_NUMBER() OVER (PARTITION BY channel ORDER BY d) AS rn,
         COUNT(*)     OVER (PARTITION BY channel)            AS cnt
  FROM f
)
SELECT channel, MAX(cnt) AS payers, AVG(d) AS median_days
FROM r
WHERE rn IN (FLOOR((cnt + 1) / 2), FLOOR((cnt + 2) / 2))
GROUP BY channel
ORDER BY median_days, channel;

함정

  • DATEDIFF(끝, 시작) — MySQL 은 인자 순서가 끝이 먼저다. TIMESTAMPDIFF 와 반대라 헷갈린다.
  • 짝수 처리를 빼먹으면 값이 한쪽으로 치우친다. FLOOR((cnt+1)/2) 와 FLOOR((cnt+2)/2) 두 자리를 잡는 게 정석.
  • 홀수면 두 식이 같은 값이 되어 자동으로 1개만 남는다. 분기할 필요 없다.
  • payers 는 COUNT(*) 가 아니라 MAX(cnt). WHERE 로 이미 2행만 남았기 때문.

이렇게 변형된다

“상위 25% 지점”이면 PERCENT_RANK() <= 0.25 또는 NTILE(4)=1.

Q7. 월별 플랜 업그레이드 / 다운그레이드보통

쉬운 설명

지난번에 뭐 썼는지와 이번에 뭐 쓰는지를 비교. 달라졌으면 '변경' 이다.

결제이번 플랜직전 플랜판정
1차basic(없음)첫 결제 — 제외
2차probasic업그레이드
3차propro그대로 — 제외
4차basicpro다운그레이드

이렇게 푼다

  1. 결제 줄마다 직전 결제의 플랜을 한 칸 위에서 끌어온다 (LAG, 사람별로 묶고 날짜 순서로).
  2. 직전 플랜이 없으면 첫 결제니까 빼 버린다.
  3. basic → pro 면 업, pro → basic 이면 다운으로 센다.
  4. 월별로 합친다.

이것만 피하면 된다

  • 변경이 0건인 달은 아예 나오면 안 된다. 걸러낼 때 업 + 다운 > 0 으로 써라.
    업 != 0 AND 다운 != 0 으로 쓰면 한쪽만 있는 달이 사라진다. 업그레이드만 5건 있는 달도 나와야 하는데 없어진다.
  • 사람별로 묶는 걸(PARTITION BY user_id) 빼먹으면 다른 사람의 플랜과 비교해 버린다.
자세한 설명
묻는 것 · 직전 행과 비교할 줄 아는가.

풀이 순서

  1. 유저별 결제 순서로 LAG(plan).
  2. 직전 플랜과 현재 플랜을 비교해 방향을 판정.
  3. 첫 결제는 직전이 NULL 이므로 제외.

정답 (MySQL)

WITH l AS (
  SELECT user_id, paid_date, plan,
         LAG(plan) OVER (PARTITION BY user_id ORDER BY paid_date) AS prev_plan
  FROM payments
)
SELECT DATE_FORMAT(paid_date, '%Y-%m') AS month,
       SUM(CASE WHEN prev_plan='basic' AND plan='pro'   THEN 1 ELSE 0 END) AS upgrades,
       SUM(CASE WHEN prev_plan='pro'   AND plan='basic' THEN 1 ELSE 0 END) AS downgrades
FROM l
WHERE prev_plan IS NOT NULL
GROUP BY month
HAVING upgrades + downgrades > 0
ORDER BY month;

함정

  • PARTITION BY user_id 누락 — 다른 유저의 플랜과 비교하게 된다.
  • 첫 결제를 변경으로 세지 않도록 prev_plan IS NOT NULL.
  • MySQL 은 HAVING 에서 SELECT 별칭을 쓸 수 있다. 표준 SQL 은 안 된다.

이렇게 변형된다

“상태가 바뀐 시점”, “가격이 인상된 건” 전부 같은 구조.

Q8. 3개월 이상 연속 결제한 유저어려움

쉬운 설명

출석 도장. 1월·2월·3월 쭉 찍었으면 3연속. 1월·3월만 찍었으면 끊긴 것. 이 트릭은 외워 두면 평생 쓴다.

결제한 달달 번호줄 번호차이
1월110
2월220
3월330
6월642

차이가 같은 것끼리 한 덩어리다. 위에서는 0 이 세 개니까 3연속. 연속이면 달 번호와 줄 번호가 똑같이 1씩 늘어서 차이가 안 변한다. 끊기면 달 번호만 껑충 뛰어서 차이가 달라진다.

이렇게 푼다

  1. 사람별로 결제한 달 목록을 중복 없이 만든다.
  2. 달을 숫자로 바꾼다 (기준월부터 몇 개월째인가).
  3. 달 숫자 − 줄 번호를 계산한다.
  4. 그 값으로 묶어서 개수를 세고, 3 이상만 남긴다.

이것만 피하면 된다

  • 중복 제거를 빼먹으면 틀린다. 같은 달에 두 번 결제한 사람은 줄 번호가 두 칸 가는데 달 숫자는 그대로라서, 안 연속인데 연속으로 잡힌다.
  • 마지막에 사람 수를 셀 때 중복을 지워라. 한 사람이 '1~3월 연속' 과 '7~9월 연속' 두 덩어리를 가질 수 있다.
자세한 설명
묻는 것 · gaps and islands. 알면 1분, 모르면 못 푼다.

풀이 순서

  1. 유저별 결제한 월 목록을 중복 없이 만든다.
  2. 월을 일련번호로 바꾼다 (기준월로부터 몇 개월째인가).
  3. 일련번호 − ROW_NUMBER() → 연속 구간마다 같은 값이 나온다.
  4. 그 값으로 묶어 개수를 세고 3 이상만 남긴다.

정답 (MySQL)

WITH mu AS (
  SELECT DISTINCT user_id, DATE_FORMAT(paid_date, '%Y-%m-01') AS m FROM payments
),
g AS (
  SELECT user_id, m,
         TIMESTAMPDIFF(MONTH, '2026-01-01', m)
         - ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY m) AS grp
  FROM mu
),
runs AS (
  SELECT user_id, grp, COUNT(*) AS run_len FROM g GROUP BY user_id, grp
)
SELECT COUNT(DISTINCT user_id) AS users_with_3plus_streak
FROM runs WHERE run_len >= 3;

함정

  • 왜 되는지를 알아야 응용된다. 연속이면 일련번호와 행번호가 같은 보폭으로 증가해 차이가 고정된다. 끊기면 차이가 점프한다.
    2,3,4월 → 1,2,3 − 1,2,3 = 0,0,0 (같은 그룹)
    2월, 5월 → 1,4 − 1,2 = 0,2 (다른 그룹)
  • 월 중복 제거(DISTINCT)를 안 하면 같은 달 두 번 결제한 유저가 연속으로 잘못 잡힌다.
  • 마지막에 COUNT(DISTINCT user_id) — 한 유저가 연속 구간을 두 개 가질 수 있다.

이렇게 변형된다

“연속 출석 일수”, “N일 연속 접속” 전부 동일. 일 단위면 DATEDIFF 를 일련번호로.

Q9. 채널별 결제 전환과 LTV보통

쉬운 설명

돈 쓴 손님만 모아서 1인당 평균 얼마 썼나. 안 쓴 손님은 평균에서 뺀다.

분자분모
결제 비중결제한 사람전체 유저
LTV총 결제액결제한 사람

같은 문제 안에서 분모가 두 번 바뀐다. 여기서 헷갈린다.

이렇게 푼다

  1. 사람마다 총 결제액을 구한다.
  2. 유저 명단 왼쪽에 두고 붙인다 (전체 유저 수를 세야 하므로).
  3. 전체 유저 수 / 결제한 사람 수를 각각 센다.
  4. LTV = 총 결제액 ÷ 결제한 사람 수.

이것만 피하면 된다

  • LTV 의 분모는 결제한 사람이다. 전체 유저로 나누면 그건 ARPU 라는 다른 지표다. 문제를 다시 읽어라 — 어느 쪽을 묻는지가 갈린다.
  • * 1.0 또는 100.0 을 꼭 넣어라.
자세한 설명
묻는 것 · 분모가 다른 지표 두 개를 한 쿼리에서 만들 줄 아는가.

풀이 순서

  1. 유저별 누적 결제액을 먼저 만든다.
  2. users 에 LEFT JOIN.
  3. COUNT(*) 는 전체 유저, COUNT(결제컬럼) 은 결제 유저. NULL 을 세지 않는 성질을 이용한다.
  4. AVG 도 NULL 을 무시하므로 결제 유저 기준 평균이 자동으로 나온다.

정답 (MySQL)

WITH pu AS (
  SELECT user_id, SUM(amount) AS amt FROM payments GROUP BY user_id
)
SELECT u.channel,
       COUNT(*)                                       AS total_users,
       COUNT(pu.user_id)                              AS paying_users,
       ROUND(100.0 * COUNT(pu.user_id) / COUNT(*), 2) AS paying_ratio,
       ROUND(AVG(pu.amt), 2)                          AS ltv
FROM users u
LEFT JOIN pu ON pu.user_id = u.user_id
GROUP BY u.channel
ORDER BY ltv DESC;

함정

  • 이 문제의 핵심은 COUNT(*) 와 COUNT(컬럼) 의 차이다. 분모 두 개를 CASE 없이 만들 수 있다.
  • LTV 분모를 전체 유저로 착각하기 쉽다. 문제를 다시 읽을 것.
  • AVG(COALESCE(amt,0)) 로 쓰면 결제 안 한 유저가 0 으로 들어가 LTV 가 내려간다. 의도가 다르다.

이렇게 변형된다

“ARPU vs ARPPU” 가 정확히 이 차이다. ARPU 는 전체 유저, ARPPU 는 결제 유저 기준.

Q10. 채널별 ARPPU와 순위 변동어려움

쉬운 설명

반별 평균 점수로 등수를 매기고, 지난달 등수보다 올랐나 내렸나를 본다.

월채널평균등수지난달 등수변동
1월referral23,0001(없음)(없음)
2월referral23,200110
2월sns16,90043-1 (내려감)

변동 = 지난달 등수 − 이번달 등수. 등수가 1→4 로 내려가면 음수.

이렇게 푼다

  1. 월·채널별 평균을 먼저 만든다.
  2. 월 안에서 등수를 매긴다 — RANK() OVER (PARTITION BY 월 ORDER BY 평균 DESC).
  3. 채널별로 지난달 등수를 끌어온다 — LAG(등수) OVER (PARTITION BY 채널 ORDER BY 월).
  4. 지난달 등수 − 이번달 등수.

이것만 피하면 된다

  • 묶는 기준이 두 번 바뀐다. 등수를 매길 때는 월로 묶고, 지난달 등수를 끌어올 때는 채널로 묶는다. 둘을 같게 쓰면 전부 틀린다.
  • 첫 달은 지난달 등수가 NULL 이고, 변동도 NULL 이다.
자세한 설명
묻는 것 · 윈도우를 두 단계로 겹쳐 쓸 줄 아는가.

풀이 순서

  1. 월×채널 ARPPU 를 먼저 집계.
  2. 월 안에서 RANK() → 파티션은 월.
  3. 채널 기준으로 LAG(rnk) → 파티션은 채널. 파티션 기준이 다르다.
  4. 윈도우 결과를 다시 윈도우에 넣으려면 한 단계 감싸야 한다.

정답 (MySQL)

WITH a AS (
  SELECT DATE_FORMAT(p.paid_date, '%Y-%m-01') AS mm, u.channel,
         ROUND(SUM(p.amount) / COUNT(DISTINCT p.user_id), 2) AS arppu
  FROM payments p JOIN users u ON u.user_id = p.user_id
  GROUP BY mm, u.channel
),
r AS (
  SELECT mm, channel, arppu,
         RANK() OVER (PARTITION BY mm ORDER BY arppu DESC) AS rnk
  FROM a
)
SELECT DATE_FORMAT(mm, '%Y-%m') AS month, channel, arppu, rnk,
       LAG(rnk) OVER (PARTITION BY channel ORDER BY mm)       AS prev_rnk,
       LAG(rnk) OVER (PARTITION BY channel ORDER BY mm) - rnk AS rank_change
FROM r
ORDER BY mm, rnk;

함정

  • 같은 SELECT 안에서 RANK 를 LAG 에 넣을 수 없다. CTE 로 한 단계 감싼다. 이 문제가 묻는 게 바로 이것.
  • 순위는 월로 파티션, 변동은 채널로 파티션. 둘을 같게 쓰면 전부 틀린다.
  • rank_change 부호 방향을 문제대로. 여기서는 ‘전월 − 이번달’이라 오르면 양수.
  • ARPPU 분모는 COUNT(DISTINCT user_id). 결제 건수가 아니다.

이렇게 변형된다

“전월 대비 매출 순위 변동”, “주간 랭킹 변화” 전부 같은 2단 구조.

Q11. 5일 이동평균 (부분 구간)보통

쉬운 설명

최근 5일 평균. 아직 5일이 안 모인 날은 있는 날만 가지고 평균.

날종가평균에 쓰는 개수ma5
1일차1001개100.00
2일차2002개150.00
5일차…5개…
6일차…5개 (1일차는 빠짐)…

창문이 5칸이고, 날짜가 가면 창문도 같이 미끄러진다. 시작할 때는 창문이 아직 다 안 찼다.

이렇게 푼다

  1. AVG(close_price) OVER (ORDER BY trade_date ROWS BETWEEN 4 PRECEDING AND CURRENT ROW) — 이 한 줄이 전부다.
  2. 소수점 둘째 자리까지 반올림.

이것만 피하면 된다

  • ROWS BETWEEN … 을 빼면 전혀 다른 값이 나온다. 안 쓰면 기본값이 '처음부터 이번 줄까지' 라서 누적 평균이 되어 버린다. 이게 이동평균 문제에서 가장 많이 틀리는 부분이다.
  • 4 PRECEDING 이다. 5 가 아니다. 오늘을 포함해서 5개니까 앞으로 4칸이다.
  • 날짜를 빼서 구하면 안 된다. 주말에는 데이터가 없어서 '5일 전' 자리가 비어 있다. 줄 개수로 세야 한다.
자세한 설명
묻는 것 · 프레임을 쓸 줄 아는가. 날짜가 아니라 행으로 세는가.

풀이 순서

  1. AVG(x) OVER (ORDER BY 날짜 ROWS BETWEEN 4 PRECEDING AND CURRENT ROW).
  2. 끝.

정답 (MySQL)

SELECT trade_date, close_price,
       ROUND(AVG(close_price) OVER (ORDER BY trade_date
             ROWS BETWEEN 4 PRECEDING AND CURRENT ROW), 2) AS ma5
FROM prices
WHERE stock_code = '005930'
ORDER BY trade_date;

함정

  • ROWS 누락 — 기본 프레임이 RANGE UNBOUNDED PRECEDING 이라 누적평균이 된다. 가장 흔한 실수.
  • 5 PRECEDING 으로 쓰면 6일 평균. 당일이 포함되므로 4 PRECEDING.
  • 날짜 조인으로 풀려고 하면 안 된다. INTERVAL 4 DAY 는 달력 4일이라 주말이 끼면 거래일 수가 맞지 않는다.
  • 부분 구간 처리는 따로 할 필요가 없다. 앞 행이 모자라면 윈도우가 알아서 줄어든다. CASE 분기는 오히려 틀린다.
  • 반대로 “초반 4일은 NULL” 이라는 문제면 CASE WHEN ROW_NUMBER() OVER (...) >= 5 THEN ... END 를 덧붙인다.

이렇게 변형된다

“최근 7일 합계”, “최근 3건 평균” 전부 같은 프레임.

Q12. 종목별 5일·20일 이동평균보통

쉬운 설명

  2. AVG(close_price) OVER (PARTITION BY stock_code ORDER BY trade_date ROWS BETWEEN 4 PRECEDING AND CURRENT ROW)

  • PARTITION BY 를 두 식 모두에 넣어라. ma5 에만 넣고 ma20 에 빼먹는 실수가 흔하다.
  • 정렬도 종목 ASC, 날짜 ASC 둘 다 써야 한다.
자세한 설명
묻는 것 · Q11 에 PARTITION 을 추가할 줄 아는가.

풀이 순서

  1. Q11 과 같되 PARTITION BY stock_code 를 넣는다.

정답 (MySQL)

SELECT stock_code, trade_date, close_price,
       ROUND(AVG(close_price) OVER (PARTITION BY stock_code ORDER BY trade_date
             ROWS BETWEEN  4 PRECEDING AND CURRENT ROW), 2) AS ma5,
       ROUND(AVG(close_price) OVER (PARTITION BY stock_code ORDER BY trade_date
             ROWS BETWEEN 19 PRECEDING AND CURRENT ROW), 2) AS ma20
FROM prices
ORDER BY stock_code, trade_date;

함정

  • PARTITION 누락 — 종목 경계를 넘어 평균이 섞인다. 삼성전자 첫날 ma5 에 SK하이닉스 종가가 들어간다.
  • WHERE 로 한 종목만 거르는 Q11 과 달리 여기서는 전 종목이 섞여 있다. 반드시 파티션.

이렇게 변형된다

“지점별 7일 평균 매출”, “유저별 최근 3건 평균” 전부 동일.

Q13. 골든크로스 발생일어려움

쉬운 설명

단기선이 장기선을 아래에서 위로 뚫는 날. 어제는 아래에 있었고 오늘 위로 올라온 바로 그 날 하나.

날ma5 vs ma20판정
월ma5 < ma20 (아래)
화ma5 > ma20 (위)골든크로스!
수ma5 > ma20 (위)이미 위 — 아니다
목ma5 > ma20 (위)이미 위 — 아니다

'위에 있는 날' 이 아니라 '올라온 날' 을 찾는 문제다. 그래서 어제와 비교해야 한다.

이렇게 푼다

  1. 먼저 ma5 와 ma20 을 만든다 (Q12 와 같은 방식).
  2. 그 결과를 한 번 감싸고, 어제의 ma5·ma20 을 한 칸 위에서 끌어온다.
  3. 어제는 ma5 <= ma20 이었고 오늘은 ma5 > ma20 인 날만 남긴다.

이것만 피하면 된다

  • 오늘만 보고 ma5 > ma20 으로 하면 틀린다. 계속 위에 있는 날이 전부 걸려서 결과가 몇 배로 많아진다.
  • 비교는 반올림 전 값으로 한다. 반올림한 값으로 비교하면 두 값이 같아져서 교차를 놓친다. 보여줄 때만 반올림한다.
  • 종목마다 따로 (PARTITION BY stock_code). 그리고 첫 거래일은 어제가 없으니 빠진다.
자세한 설명
묻는 것 · 윈도우 결과에 다시 LAG 를 거는가. 그리고 ‘교차’의 정의.

풀이 순서

  1. ma5, ma20 을 만든다 (CTE 1).
  2. 그 위에 LAG 로 전일 ma5, ma20 을 가져온다 (CTE 2).
  3. 전일 ma5 <= ma20 그리고 당일 ma5 > ma20.

정답 (MySQL)

WITH m AS (
  SELECT stock_code, trade_date,
         AVG(close_price) OVER (PARTITION BY stock_code ORDER BY trade_date
               ROWS BETWEEN  4 PRECEDING AND CURRENT ROW) AS ma5,
         AVG(close_price) OVER (PARTITION BY stock_code ORDER BY trade_date
               ROWS BETWEEN 19 PRECEDING AND CURRENT ROW) AS ma20
  FROM prices
),
d AS (
  SELECT m.*,
         LAG(ma5)  OVER (PARTITION BY stock_code ORDER BY trade_date) AS prev_ma5,
         LAG(ma20) OVER (PARTITION BY stock_code ORDER BY trade_date) AS prev_ma20
  FROM m
)
SELECT stock_code, trade_date, ROUND(ma5, 2) AS ma5, ROUND(ma20, 2) AS ma20
FROM d
WHERE prev_ma5 IS NOT NULL AND prev_ma5 <= prev_ma20 AND ma5 > ma20
ORDER BY stock_code, trade_date;

함정

  • 당일 조건만 쓰면 안 된다. ma5 > ma20 만 보면 이미 올라가 있는 구간이 전부 걸린다. ‘뚫고 올라간 그 날’이어야 한다.
  • trade_date + INTERVAL 1 DAY 로 전일을 찾으면 월요일과 공휴일 다음날이 통째로 누락된다. 실제로 거래일의 20% 가 빠진다. 반드시 LAG.
  • 반올림은 출력할 때만. 비교는 반올림 전 값으로 해야 경계에서 안 틀린다.
  • WHERE 에서 윈도우 함수를 못 쓰므로 CTE 2 단이 필요하다.

이렇게 변형된다

데드크로스는 부등호만 뒤집는다. “임계값을 상향 돌파한 날”도 같은 패턴.

Q14. 전 유저 결제 요약 (NULL 처리)보통

쉬운 설명

전교생 명단에 성적을 붙이는데, 시험 안 본 애도 명단에 남아야 한다. 점수 칸은 0 으로, 시험 날짜 칸은 빈칸으로.

더할 게 하나도 없을 때 뭐가 나오나 — 이걸 알아야 풀린다.

함수아무것도 없을 때
COUNT(*) · COUNT(칸)0
SUM · AVG · MAX · MINNULL (0 이 아니다!)

이렇게 푼다

  1. 유저 명단을 왼쪽에 두고 결제를 붙인다 (LEFT JOIN).
  2. 건수는 COUNT — 결제가 없으면 자동으로 0 이 된다.
  3. 금액은 COALESCE(SUM(금액), 0) — SUM 밖에 씌운다.
  4. 마지막 결제일은 NULL 그대로 둔다.
  5. 결제 없는 사람을 뒤로 보내고, 금액 많은 순, 상위 20명만.

이것만 피하면 된다

  • SUM 은 더할 게 없으면 0 이 아니라 NULL 이다. 그래서 COALESCE(…, 0) 이 필요하다. 이것 때문에 금액 칸이 빈칸으로 나오는 실수가 가장 흔하다.
  • 결제 없는 사람을 뒤로 보내는 요령: ORDER BY (마지막결제일 IS NULL), 금액 DESC, user_id ASC — IS NULL 은 0 또는 1 이라서, 결제 있는 사람(0)이 먼저 온다.
  • LIMIT 20 빼먹지 마라. 안 쓰면 3,000줄이 다 나온다.
자세한 설명
묻는 것 · LEFT JOIN 후 NULL 을 어떻게 다루는가. 그리고 NULL 정렬.

풀이 순서

  1. users 기준 LEFT JOIN.
  2. 건수는 COUNT(p.user_id) — NULL 을 안 세므로 0 이 된다.
  3. 합계는 COALESCE(SUM(...), 0) — SUM 은 대상이 없으면 NULL 을 반환한다.
  4. 마지막 결제일은 NULL 그대로 두되, 정렬에서 뒤로 보낸다.

정답 (MySQL)

SELECT u.user_id, u.channel,
       COUNT(p.user_id)           AS pay_count,
       COALESCE(SUM(p.amount), 0) AS total_amount,
       MAX(p.paid_date)           AS last_paid
FROM users u
LEFT JOIN payments p ON p.user_id = u.user_id
GROUP BY u.user_id, u.channel
ORDER BY (MAX(p.paid_date) IS NULL), COALESCE(SUM(p.amount),0) DESC, u.user_id
LIMIT 20;

함정

  • COUNT(*) 를 쓰면 결제 없는 유저도 1 이 된다. LEFT JOIN 으로 행은 하나 생기기 때문. COUNT(p.user_id) 여야 0.
  • SUM 은 대상 행이 없으면 0 이 아니라 NULL. COALESCE 로 감싼다.
  • MySQL 에 NULLS LAST 가 없다. ORDER BY (컬럼 IS NULL), 컬럼 로 쓴다. 조건식이 0/1 이 되어 NULL 이 뒤로 간다.
  • COALESCE(total, '없음') 처럼 문자 기본값을 넣으면 컬럼 전체가 문자열이 되어 정렬이 사전순으로 깨진다.

이렇게 변형된다

“주문 없는 고객 포함 요약”, “미거래 종목 포함” 전부 동일.

Q15. 채널별 pro 비중 (0 나누기)보통

쉬운 설명

결제한 사람 중에 비싼 요금제 쓴 비율. 결제한 사람이 0명인 채널은 계산이 불가능하니 빈칸이어야 한다.

채널결제 유저pro 유저비중
organic37113035.04
newsletter00NULL

0 ÷ 0 은 '0%' 가 아니다. 계산할 수 없음 이다. 그래서 0 이 아니라 빈칸(NULL)이 맞다. 그리고 그 채널도 결과에 나와야 한다.

이렇게 푼다

  1. 채널을 전부 남긴다 (결제 유저가 0명인 채널도).
  2. 채널별로 결제한 사람 수, 그중 pro 쓴 사람 수를 센다.
  3. pro수 * 100.0 / NULLIF(결제수, 0).

이것만 피하면 된다

  • NULLIF(분모, 0) 이 이 문제의 전부다. '분모가 0 이면 NULL 로 바꿔라' 는 뜻이고, NULL 로 나누면 결과가 NULL 이 된다. 이름이 헷갈리는데, NULLIF 는 NULL 을 만드는 함수다.
  • IFNULL 과 반대다. IFNULL(분모, 0) 은 NULL 을 0 으로 바꿔서 0 나누기를 일부러 만든다. 정반대다.
  • 결제 유저 0명인 채널을 WHERE 로 걸러내면 안 된다. 그 줄도 나와야 한다.
자세한 설명
묻는 것 · 분모가 0 이 될 수 있는 상황을 아는가.

풀이 순서

  1. 결제 유저 수와 pro 유저 수를 조건부 DISTINCT 집계로.
  2. 비율 계산에서 분모를 NULLIF(분모, 0) 로 감싼다.

정답 (MySQL)

SELECT u.channel,
       COUNT(DISTINCT p.user_id) AS paying_users,
       COUNT(DISTINCT CASE WHEN p.plan='pro' THEN p.user_id END) AS pro_users,
       ROUND(100.0 * COUNT(DISTINCT CASE WHEN p.plan='pro' THEN p.user_id END)
             / NULLIF(COUNT(DISTINCT p.user_id), 0), 2) AS pro_ratio
FROM users u
LEFT JOIN payments p ON p.user_id = u.user_id
GROUP BY u.channel
ORDER BY pro_ratio DESC, u.channel;

함정

  • IFNULL(분모, 0) 은 정반대다. 0 나누기를 막는 게 아니라 만든다. 방어는 NULLIF(분모, 0).
  • 결제 유저가 0 명인 채널도 결과에 나와야 하므로 LEFT JOIN.
  • CASE WHEN ... THEN user_id END 에 ELSE 를 쓰지 않는다. ELSE 0 을 넣으면 0 도 값이라 DISTINCT 집계에 섞인다.
  • 이 데이터로는 ‘분모 0’ 이 드물다. 안 걸린다고 맞는 게 아니다 — 여러 데이터셋으로 채점되면 그때 터진다.

이렇게 변형된다

“환불률”, “쿠폰 사용률” 처럼 모집단이 비어 있을 수 있는 비율 전부.

Q16. 퍼널 단계별 유저 수와 단계 전환율쉬움

쉬운 설명

들어온 사람 → 구경한 사람 → 장바구니에 담은 사람 → 산 사람. 각 칸에 몇 명.

단계사람 수앞 단계 대비
app_open2,834
item_view1,87266.1%
add_to_cart83744.7%
purchase32038.2%

표 하나에 한 줄로 나와야 한다. 테이블은 한 번만 읽으면 된다.

이렇게 푼다

  1. 한 번 읽으면서 네 숫자를 동시에 만든다 — COUNT(DISTINCT CASE WHEN 행동='app_open' THEN user_id END) 식으로 네 개.
  2. 그 네 개를 서브쿼리로 감싸서 바깥에서 이름으로 다시 쓴다. 안 감싸면 전환율 식에 같은 걸 또 써야 해서 쿼리가 네 배로 길어진다.
  3. ROUND(100.0 * 뒤 / NULLIF(앞, 0), 1).

이것만 피하면 된다

  • DISTINCT 를 빼면 안 된다. 한 사람이 app_open 을 네 번 남기면 4 로 세어진다. 묻는 건 사람 수다.
  • CASE 에 ELSE 0 을 쓰지 마라. 0 도 값이라서 '0 번 사람' 한 명으로 세어진다. ELSE 를 안 쓰면 NULL 이 되고, COUNT 는 NULL 을 안 센다.
자세한 설명
묻는 것 · 한 테이블을 한 번만 읽어 네 숫자를 뽑고, 그 숫자끼리 나눈다. JOIN 도 GROUP BY 도 필요 없다. 여기서 시간을 쓰면 안 되는 문제다.

풀이 순서

  1. COUNT(DISTINCT CASE WHEN ... THEN user_id END) 로 단계별 순 유저 수를 한 줄씩 만든다. 테이블을 네 번 읽을 필요가 없다.
  2. 그 네 숫자를 서브쿼리로 감싸서 바깥에서 이름으로 다시 쓴다. 그러지 않으면 전환율 식에 COUNT(DISTINCT CASE...) 를 또 써야 해서 길이가 네 배가 된다.
  3. 전환율은 100.0 * 을 앞에 붙이고 ROUND(..., 1).
  4. 분모에 NULLIF(분모, 0) 을 씌운다.

정답 (MySQL)

SELECT a AS app_open_users,
       v AS item_view_users,
       k AS cart_users,
       p AS purchase_users,
       ROUND(100.0 * v / NULLIF(a, 0), 1) AS view_conversion_rate,
       ROUND(100.0 * k / NULLIF(v, 0), 1) AS cart_conversion_rate,
       ROUND(100.0 * p / NULLIF(k, 0), 1) AS purchase_conversion_rate
FROM (
  SELECT COUNT(DISTINCT CASE WHEN event_name = 'app_open'    THEN user_id END) AS a,
         COUNT(DISTINCT CASE WHEN event_name = 'item_view'   THEN user_id END) AS v,
         COUNT(DISTINCT CASE WHEN event_name = 'add_to_cart' THEN user_id END) AS k,
         COUNT(DISTINCT CASE WHEN event_name = 'purchase'    THEN user_id END) AS p
  FROM user_event_logs
) c;

함정

  • DISTINCT 를 빼면 틀린다. 한 유저가 app_open 을 네 번 남기면 COUNT(CASE ...) 는 4 를 센다. 묻는 건 유저 수이지 이벤트 수가 아니다.
  • CASE 에 ELSE 를 쓰지 마라. ELSE 0 을 붙이면 0 도 값이라서 COUNT(DISTINCT ...) 가 0 을 하나의 유저로 센다. ELSE 를 안 쓰면 NULL 이 되고 COUNT 는 NULL 을 세지 않는다.
  • 100.0 의 소수점이 핵심이다. 100 * v / a 는 정수 나눗셈이 되는 엔진에서 0 이 나온다. 토스 테스트돔에서 실제로 이걸로 틀린 적이 있다.
  • 이 문제의 NULLIF 는 채점으로 확인할 수 없다. MySQL·SQLite 는 0 으로 나누면 오류 없이 NULL 을 준다. PostgreSQL·MS SQL 은 오류가 난다. 즉 여기서는 있어도 없어도 같은 답이 나오지만, 습관을 안 들이면 다른 엔진에서 터진다.
  • 이 문제의 '퍼널' 은 진짜 퍼널이 아니다. 단계 순서를 안 따지므로, 장바구니를 안 거치고 구매한 유저가 있으면 뒤 단계가 앞 단계보다 많아져 전환율이 100% 를 넘을 수 있다. 면접에서 이걸 물으면 '순서를 강제하려면 단계별 첫 시각을 비교해야 한다' 고 답하면 된다.

이렇게 변형된다

“단계별 이탈률”은 100 − 전환율. “채널별 퍼널”이면 GROUP BY channel 만 추가되고 구조는 그대로다. 순서를 강제하는 진짜 퍼널은 단계별 MIN(created_at) 을 구해 MIN(cart) > MIN(view) 처럼 비교한다.

Q17. 코호트별 D7 리텐션율보통

쉬운 설명

첫 거래한 날로부터 딱 7일 뒤 다시 왔나. 첫 거래일마다 따로 센다.

첫 거래확인할 날왔으면
2월 1일2월 8일재방문 1명
2월 2일2월 9일아무도 안 옴 → 0

'7일 안에' 가 아니라 '딱 그 날'. 2월 7일에 왔어도 안 세고, 2월 9일에 왔어도 안 센다. 재방문 0명인 날도 0 으로 한 줄 나와야 한다.

이렇게 푼다

  1. 코호트 명단(first_trades)을 왼쪽에 둔다. 분모가 여기서 나온다.
  2. 방문 기록을 붙이는데, 조건을 ON 안에 쓴다 — ON 같은사람 AND 방문일 = 첫거래일 + 7일.
  3. 분모 = 명단 사람 수, 분자 = 붙은 사람 수. 둘 다 중복 지우고 센다.

이것만 피하면 된다

  • 조건을 WHERE 에 쓰면 LEFT JOIN 이 그냥 JOIN 이 되어 버린다. 안 온 사람은 방문일이 빈칸인데, WHERE 가 그 빈칸을 걸러내서 분모에서까지 사라진다. → 오른쪽 테이블 조건은 반드시 ON 에. 이 한 줄이 리텐션 문제의 핵심이다.
  • 분자에 중복 제거를 빼면 100% 를 넘는다. 같은 사람이 같은 날 여러 번 방문 기록을 남길 수 있다. 리텐션이 100 을 넘으면 거의 항상 이 실수다.
  • 분모를 COUNT(*) 로 쓰면 안 된다. 붙이면서 늘어난 줄 수가 나온다.
자세한 설명
묻는 것 · 코호트 테이블을 왼쪽에 두고 활동 로그를 LEFT JOIN 한다. 코호트 문제의 90% 가 이 모양이다.

풀이 순서

  1. 코호트 테이블(first_trades)을 왼쪽에 둔다. 분모가 여기서 나온다.
  2. 활동 로그를 LEFT JOIN 하고, 조인 조건에 visit_date = first_trade_date + 7일 을 넣는다.
  3. 분모는 COUNT(DISTINCT f.user_id), 분자는 COUNT(DISTINCT v.user_id). 둘 다 DISTINCT 다.
  4. 범위 조건은 WHERE 에 쓴다 (왼쪽 테이블 조건이므로 안전하다).

정답 (MySQL)

SELECT f.first_trade_date,
       COUNT(DISTINCT f.user_id) AS cohort_size,
       COUNT(DISTINCT v.user_id) AS d7_active_users,
       ROUND(100.0 * COUNT(DISTINCT v.user_id)
             / NULLIF(COUNT(DISTINCT f.user_id), 0), 1) AS d7_retention_rate
FROM first_trades f
LEFT JOIN daily_app_visits v
       ON v.user_id = f.user_id
      AND v.visit_date = DATE_ADD(f.first_trade_date, INTERVAL 7 DAY)
WHERE f.first_trade_date BETWEEN '2026-02-01' AND '2026-02-07'
GROUP BY f.first_trade_date
ORDER BY f.first_trade_date;

함정

  • JOIN 조건을 WHERE 로 옮기면 LEFT JOIN 이 INNER JOIN 이 된다. WHERE v.visit_date = ... 로 쓰면 재방문 안 한 유저의 NULL 행이 조건에 걸려 사라지고, 분모까지 같이 깎인다. 오른쪽 테이블 조건은 반드시 ON 에 — 이 한 줄이 리텐션 문제의 핵심이다.
  • '정확히 7일' 과 '7일 이내' 는 다른 문제다. = 로 쓸 자리에 <= 를 쓰면 숫자가 크게 부풀어 오른다. 문제를 다시 읽어라.
  • 분자에 DISTINCT 를 빼면 100% 를 넘는다. 방문 로그는 같은 유저가 같은 날 여러 행을 남길 수 있다. 리텐션율이 100 을 넘으면 거의 항상 이 실수다.
  • 분모를 COUNT(*) 로 쓰면 안 된다. LEFT JOIN 후의 COUNT(*) 는 조인으로 불어난 행 수다. 코호트 크기가 아니다.
  • 재방문자 0 명인 날도 한 행 나와야 한다. LEFT JOIN 이면 자동으로 0 이 된다. COUNT 는 빈 입력에서 0 을 돌려주기 때문이다 (SUM 은 NULL 이 된다 — 다른 문제에서 자주 나오는 함정).

이렇게 변형된다

“D1/D7/D30 을 한 번에”면 조인 조건을 visit_date IN (+1일, +7일, +30일) 로 바꾸고 COUNT(DISTINCT CASE WHEN ... END) 를 세 개 만든다. “월 코호트 매트릭스”면 TIMESTAMPDIFF(MONTH, 코호트월, 활동월) 을 경과 개월로 쓰고 그걸로 피벗한다.

Q18. 유저별 최장 연속 거래일수어려움

쉬운 설명

Q8 의 출석 도장 트릭과 똑같다. 단위가 '달' 에서 '날' 로 바뀐 것뿐.

거래한 날날 번호줄 번호차이
3월 2일60159
3월 3일61259
3월 4일62359
3월 8일66462

차이 59 가 세 개 → 3연속. 그 다음은 끊긴 것.

이렇게 푼다

  1. 성공한 주문만 남기고, 하루는 1번으로 중복을 지운다. 이 한 줄에 문제 조건 두 개가 다 들어 있다.
  2. 날짜를 숫자로 바꾼다.
  3. 날 숫자 − 줄 번호 → 묶어서 개수 → 사람별 최대값 → 3 이상만.

이것만 피하면 된다

  • 취소된 주문을 빼라. 그 날 주문이 전부 취소면 거래 안 한 날이고, 연속이 거기서 끊겨야 한다.
  • 하루 여러 건을 1건으로 지워라. 하루에 3건 거래했으면 줄 번호가 3칸 가는데 날짜는 그대로여서 연속일수가 부풀어 오른다.
  • 동점이 아주 많은 문제다. 최장일수 DESC, user_id ASC 둘 다 써라.
자세한 설명
묻는 것 · gaps and islands. 알면 2분, 모르면 못 푼다. 반드시 외워 둘 패턴.

풀이 순서

  1. 먼저 조건을 걸고 하루 단위로 중복을 지운다: SELECT DISTINCT user_id, order_date ... WHERE status='COMPLETED'. 이 한 줄에 문제의 조건 두 개가 다 들어 있다.
  2. 날짜를 일련번호로 바꾼다: DATEDIFF(order_date, '기준일').
  3. 일련번호 − ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY order_date) → 연속 구간마다 같은 값이 나온다.
  4. 그 값으로 묶어 COUNT(*) → 구간 길이. 유저별 MAX() → 최장 길이. HAVING 으로 3 이상만.

정답 (MySQL)

WITH d AS (
  SELECT DISTINCT user_id, order_date
  FROM stock_orders
  WHERE status = 'COMPLETED'
),
g AS (
  SELECT user_id, order_date,
         DATEDIFF(order_date, '2026-01-01')
         - ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY order_date) AS grp
  FROM d
),
runs AS (
  SELECT user_id, grp, COUNT(*) AS run_len
  FROM g GROUP BY user_id, grp
)
SELECT user_id, MAX(run_len) AS max_streak_days
FROM runs
GROUP BY user_id
HAVING MAX(run_len) >= 3
ORDER BY max_streak_days DESC, user_id ASC;

함정

  • 왜 되는가. 연속이면 날짜 일련번호와 행 번호가 같은 보폭으로 늘어나 차이가 고정된다. 끊기면 차이가 점프한다.
    3/2,3/3,3/4 → 60,61,62 − 1,2,3 = 59,59,59 (한 구간)
    3/2, 3/6 → 60,64 − 1,2 = 59,62 (다른 구간)
  • DISTINCT 를 빼면 연속일수가 부풀어 오른다. 하루에 3건 거래했으면 ROW_NUMBER 가 세 칸 가는데 날짜는 그대로라 차이가 틀어진다.
  • status 필터를 빼면 끊겨야 할 구간이 이어진다. 그 날 주문이 전부 CANCELLED 면 거래하지 않은 날이다. 「끊김복귀」 데이터셋이 이걸 잡는다.
  • HAVING 에 MAX(run_len) 을 그대로 쓴다. WHERE run_len >= 3 으로 미리 걸러도 같은 답이 나오지만, 그러면 '최장 구간이 3 미만인 유저' 와 '3 이상 구간만 남긴 유저' 의 MAX 가 달라질 수 있는 변형 문제에서 틀린다.
  • 정렬 두 개를 다 쓴다. 동점이 많은 문제다. max_streak_days DESC 만 쓰면 같은 값들 사이 순서가 실행마다 바뀐다.

이렇게 변형된다

“연속 출석일수”, “N일 연속 접속”, “연속 결제 개월수” 전부 같은 패턴이다. 월 단위면 일련번호를 TIMESTAMPDIFF(MONTH, 기준월, 그달) 로 바꾼다. “현재 진행 중인 연속일수”면 마지막 구간만 (MAX(order_date) = 오늘 인 구간) 남긴다.

Q19. A/B 테스트 그룹 집계 (상위 1% 제외)보통

쉬운 설명

반 평균 낼 때 혼자 만점인 애를 빼고 계산. 단, 빼는 순서가 중요하다.

이 순서를 바꾸면 답이 달라진다.

①거래 없는 참가자를 0 으로 채운다
②그 상태에서 그룹별로 등수를 매긴다
③맨 위를 자른다
④남은 사람으로 평균

①을 빼고 ②를 하면 모집단이 달라져서 잘려나갈 사람도 달라진다.

이렇게 푼다

  1. 참가자 명단을 왼쪽에 두고 거래 금액을 붙이고 COALESCE(금액, 0).
  2. 그 결과 위에서 PERCENT_RANK() OVER (PARTITION BY 그룹 ORDER BY 금액).
  3. 한 번 더 감싸서 바깥에서 WHERE 등수 <= 0.99.
  4. 남은 것으로 인원·합계·평균.

이것만 피하면 된다

  • 등수 함수는 WHERE 에 못 쓴다. WHERE PERCENT_RANK() OVER (…) <= 0.99 는 문법 오류다. 실행 순서가 WHERE 먼저, 등수 나중이라서 그렇다. 한 단 감싸는 것 외에 방법이 없다.
  • 거래 없는 참가자를 빼면 안 된다. 실험에 참가한 사람은 거래를 안 했어도 참가자다. 분모를 임의로 줄이면 A/B 결과를 못 쓴다.
  • 알아 둘 것: PERCENT_RANK 는 맨 위가 항상 정확히 1.0 이다. 그래서 > 0.99 는 '상위 1%' 가 아니라 거의 항상 맨 위 한 명만 자른다. 문제가 그렇게 시켰으니 그대로 풀되, 이게 허술한 정의라는 건 알고 있어라. 면접에서 물으면 '진짜 상위 1% 는 NTILE(100) 로 자른다' 고 답하면 된다.
자세한 설명
묻는 것 · 순서가 생명인 문제. ①0 채우기 → ②순위 매기기 → ③자르기 → ④집계. 이 순서를 바꾸면 답이 달라진다.

풀이 순서

  1. 실험 참가자 테이블을 왼쪽에 두고 거래 요약을 LEFT JOIN, COALESCE(금액, 0) 으로 0 을 채운다. 분모는 참가자 수여야 한다.
  2. 그 결과 위에서 PERCENT_RANK() OVER (PARTITION BY group_name ORDER BY amt). 0 을 채운 뒤에 순위를 매기는 것이 중요하다 — 0 인 유저도 모집단의 일부다.
  3. WHERE pr <= 0.99 로 이상치를 떨어뜨린다. 윈도우 함수는 WHERE 에서 못 쓰므로 반드시 서브쿼리/CTE 로 한 단 감싸야 한다.
  4. 남은 행으로 COUNT(*), SUM(amt), 그리고 ROUND(SUM(amt)/COUNT(*), 0).

정답 (MySQL)

WITH j AS (
  SELECT e.user_id, e.group_name,
         COALESCE(s.total_trading_amount, 0) AS amt
  FROM experiment_users e
  LEFT JOIN user_trades_summary s ON s.user_id = e.user_id
),
p AS (
  SELECT group_name, amt,
         PERCENT_RANK() OVER (PARTITION BY group_name ORDER BY amt) AS pr
  FROM j
)
SELECT group_name,
       COUNT(*) AS user_count,
       SUM(amt) AS group_total_amount,
       ROUND(SUM(amt) / COUNT(*), 0) AS arpu
FROM p
WHERE pr <= 0.99
GROUP BY group_name
ORDER BY group_name;

함정

  • 윈도우 함수는 WHERE 에 못 쓴다. WHERE PERCENT_RANK() OVER (...) <= 0.99 는 문법 오류다. 실행 순서가 WHERE → 윈도우 함수이기 때문이다. 한 단 감싸는 것 외에 방법이 없다.
  • LEFT JOIN 을 INNER JOIN 으로 쓰면 유저 수가 깎인다. 거래가 없는 참가자도 실험 참가자다. A/B 테스트에서 분모를 임의로 줄이면 그 결과는 못 쓴다. 「결제없음」 데이터셋이 이걸 잡는다.
  • 0 을 채우기 전에 순위를 매기면 다른 답이 나온다. 거래 없는 유저를 빼고 순위를 매기면 모집단이 달라지고 잘려 나가는 사람도 달라진다. 문제가 지정한 순서를 따르라.
  • PERCENT_RANK 의 정의를 알고 써라. (순위 − 1) / (전체 − 1) 이므로 최솟값은 항상 0, 최댓값은 항상 1 이다. 그래서 > 0.99 는 '상위 1%' 가 아니라 거의 항상 최댓값 행만 떨어뜨린다. 그룹에 2명뿐이면 1명이 날아간다. 면접에서 물으면 '진짜 상위 1% 는 NTILE(100) 이나 PERCENTILE_CONT 로 임계값을 구해 자른다' 고 답하라.
  • 최댓값이 동점이면 둘 다 빠진다. PERCENT_RANK 는 동점에 같은 값을 주므로 공동 1위가 둘이면 둘 다 1.0 이다. 「동점」 데이터셋이 이걸 잡는다.
  • ROUND(..., 0) 은 정수가 아니라 소수 0자리다. 엔진에 따라 150 또는 150.0 으로 보인다. 정수형으로 받아야 하면 CAST(ROUND(...) AS SIGNED) 까지 써라.

이렇게 변형된다

“상·하위 1% 양쪽 제거”면 pr BETWEEN 0.01 AND 0.99. “중앙값 비교”면 ROW_NUMBER + COUNT() OVER 패턴. “전환율 비교”면 COUNT(DISTINCT 전환유저)/COUNT(DISTINCT 참가자) 로 분모를 참가자 전체로 둔다 (intention-to-treat).

Q20. 3일 이상 연속 상승 구간 모두 찾기어려움

쉬운 설명

Q8 출석 도장 트릭 + 어제와 비교. 두 개를 겹쳐 쓰는 문제다. 이게 풀리면 시계열 문제는 거의 다 풀린다.

줄번호날종가어제올랐나오른날 줄번호차이
11일100--
22일110100O11
33일120110O21
44일130120O31
55일125130X
66일130125O42

차이 1 이 세 개 → 2일~4일이 한 덩어리(3일 연속). 6일은 차이가 2 라서 다른 덩어리.

이렇게 푼다

  1. 전체 줄에 먼저 번호를 매기고, 어제 종가도 같이 끌어온다.
  2. 오른 날만 남긴다 (오늘 > 어제).
  3. 남은 것에 번호를 새로 매기고, (전체 줄번호 − 새 번호).
  4. 그 값으로 묶어서 시작일·끝일·개수, 3 이상만.

이것만 피하면 된다

  • 번호는 거르기 전에 매겨야 한다. 거른 다음에 매기면 빠진 자리가 메워져서 끊긴 구간이 붙어 버린다. 이게 핵심이고 여기서 대부분 틀린다.
  • 날짜 차이로 묶으면 틀린다. 금요일과 월요일은 날짜로는 3일 차이지만 거래일로는 바로 연속이다. 주말에 데이터가 없으니까. 줄 번호를 써야 한다.
  • 같은 가격은 상승이 아니다. > 지 >= 가 아니다.
자세한 설명
묻는 것 · LAG 로 상승일을 가리고, 그 위에 gaps and islands 를 한 번 더 얹는다. 두 패턴을 포개는 문제. 이게 풀리면 시계열 문제는 거의 다 풀린다.

풀이 순서

  1. 먼저 모든 행에 행 번호를 매긴다: ROW_NUMBER() OVER (PARTITION BY stock_code ORDER BY trade_date) AS rn. 이게 '몇 번째 거래일인가' 다. 날짜가 아니라 이 번호가 기준이 된다.
  2. 같은 단에서 LAG(close_price) OVER (PARTITION BY stock_code ORDER BY trade_date) 로 전 거래일 종가를 끌어온다.
  3. WHERE prev IS NOT NULL AND close_price > prev 로 상승일만 남긴다.
  4. 남은 상승일에 새로 행 번호를 매기고 rn − 새 행번호 → 연속 상승 구간마다 같은 값.
  5. 그 값으로 묶어 MIN/MAX/COUNT, HAVING COUNT(*) >= 3.

정답 (MySQL)

WITH p AS (
  SELECT stock_code, trade_date, close_price,
         ROW_NUMBER() OVER (PARTITION BY stock_code ORDER BY trade_date) AS rn,
         LAG(close_price) OVER (PARTITION BY stock_code ORDER BY trade_date) AS prev
  FROM stock_daily_prices
),
u AS (
  SELECT stock_code, trade_date,
         rn - ROW_NUMBER() OVER (PARTITION BY stock_code ORDER BY trade_date) AS grp
  FROM p
  WHERE prev IS NOT NULL AND close_price > prev
)
SELECT stock_code,
       MIN(trade_date) AS streak_start_date,
       MAX(trade_date) AS streak_end_date,
       COUNT(*) AS streak_days
FROM u
GROUP BY stock_code, grp
HAVING COUNT(*) >= 3
ORDER BY stock_code, streak_start_date;

함정

  • 날짜 차이로 구간을 묶으면 틀린다. 주말이 비어 있어서 금요일과 월요일은 날짜로는 3일 차이지만 거래일로는 연속이다. DATEDIFF 대신 행 번호를 일련번호로 써야 한다. 「끊김복귀」·「동점」 데이터셋이 이걸 잡는다.
  • rn 은 상승일만 걸러낸 뒤에 매기면 안 된다. 전체 행에 먼저 매겨 둬야 '거래일 순서' 가 보존된다. 걸러낸 뒤 매기면 하락일이 사라진 자리가 메워져 끊긴 구간이 붙어 버린다.
  • > 와 >= 는 다른 문제다. 전일과 같은 가격은 상승이 아니다. 「경계값」 데이터셋에 같은 가격이 들어 있다.
  • prev IS NOT NULL 을 빼면 첫 행이 섞인다. 각 종목의 첫 거래일은 전일이 없어서 LAG 가 NULL 이다. close_price > NULL 은 NULL(거짓 취급)이라 대부분 자동으로 빠지지만, 명시하는 편이 안전하고 읽기도 낫다.
  • streak_days 는 상승일의 개수다. 상승이 시작되기 전 날(기준이 된 날)은 세지 않는다. 세어야 하는 문제면 COUNT(*) + 1 이고 시작일도 하루 앞이 된다. 문제를 다시 읽어라 — 출제자가 어느 쪽을 묻는지가 갈린다.
  • PARTITION BY stock_code 를 LAG 와 ROW_NUMBER 양쪽에 다 써라. 하나라도 빠지면 종목이 넘어가는 지점에서 앞 종목의 마지막 가격과 비교해 버린다.

이렇게 변형된다

“N일 연속 하락”이면 부등호만 뒤집는다. “최장 구간 하나만”이면 마지막에 ROW_NUMBER() OVER (PARTITION BY stock_code ORDER BY COUNT(*) DESC) 로 1등만. “연속 상승률”이면 구간 양 끝 종가가 필요하므로 FIRST_VALUE/LAST_VALUE 를 쓰거나 시작일 하루 전 종가를 따로 끌어온다.

Q21. 채널별 ARPU 와 ARPPU보통

쉬운 설명

같은 매출을 전교생으로 나누면 ARPU, 돈 낸 애들로만 나누면 ARPPU. 분자는 같고 분모만 다르다.

분자분모
ARPU총 결제액전체 가입자
ARPPU총 결제액결제한 사람

가입자 100명, 결제자 20명, 매출 200만원이면 → ARPU = 2만원, ARPPU = 10만원. 다섯 배 차이가 난다.

이렇게 푼다

  1. 유저 명단 왼쪽에 두고 결제를 붙인다 (LEFT JOIN).
  2. 분모 두 개를 따로 센다 — 전체는 COUNT(DISTINCT u.user_id), 결제자는 COUNT(DISTINCT p.user_id).
  3. 왜 저게 되냐: LEFT JOIN 이라 결제 없는 사람의 p.user_id 는 빈칸이고, COUNT(DISTINCT) 는 빈칸을 안 세기 때문이다.
  4. 각각 나누고 * 1.0, ROUND(…, 2).

이것만 피하면 된다

  • AVG(금액) 은 둘 다 아니다. 그건 결제 건당 평균이다. 한 사람이 다섯 번 결제하면 그 사람이 다섯 번 반영된다. '1인당' 을 물었으면 분모를 사람 수로 직접 써야 한다.
  • AVG 는 빈칸인 줄을 분모에서도 뺀다. 값이 10, 빈칸, 20 이면 AVG 는 15 다. 10 이 아니다. 그래서 AVG 로는 ARPU 가 절대 안 나온다.
  • 결제자가 0명인 채널은 ARPPU 계산이 안 되니 결과 전체에 COALESCE(…, 0) 을 씌운다.
자세한 설명
묻는 것 · 분모가 다른 두 평균을 한 쿼리에서 만든다. 실무에서 가장 자주 틀리는 지표 쌍이고, 면접에서도 묻는다.

풀이 순서

  1. ARPU 와 ARPPU 는 분자가 같고 분모만 다르다. 분자는 둘 다 결제액 합계, 분모는 ARPU 는 전체 가입자, ARPPU 는 결제 유저.
  2. users LEFT JOIN payments 로 결제 안 한 유저까지 붙인다.
  3. 분모 두 개를 COUNT(DISTINCT u.user_id) 와 COUNT(DISTINCT p.user_id) 로 따로 센다. LEFT JOIN 이라 결제 없는 유저의 p.user_id 는 NULL 이고, COUNT(DISTINCT) 는 NULL 을 안 세므로 자동으로 결제 유저 수가 된다.
  4. * 1.0 을 붙이고 ROUND(..., 2).

정답 (MySQL)

SELECT u.channel,
       COUNT(DISTINCT u.user_id) AS users,
       COUNT(DISTINCT p.user_id) AS payers,
       ROUND(COALESCE(SUM(p.amount), 0) * 1.0
             / NULLIF(COUNT(DISTINCT u.user_id), 0), 2)     AS arpu,
       COALESCE(ROUND(SUM(p.amount) * 1.0
             / NULLIF(COUNT(DISTINCT p.user_id), 0), 2), 0) AS arppu
FROM users u
LEFT JOIN payments p ON p.user_id = u.user_id
GROUP BY u.channel
ORDER BY arpu DESC, u.channel ASC;

함정

  • AVG(p.amount) 는 ARPU 도 ARPPU 도 아니다. 결제 건당 평균이다. 한 유저가 5번 결제하면 그 유저가 5번 반영된다. '유저당' 을 물었으면 분모를 유저 수로 직접 써야 한다. 이 한 줄 차이로 숫자가 두 배 넘게 벌어진다.
  • AVG 는 NULL 을 분모에서도 뺀다. 결제 안 한 유저의 amount 는 LEFT JOIN 뒤 NULL 이고, AVG 는 그 행을 분모에서 제외한다. 그래서 AVG(p.amount) 로는 ARPU 가 절대 안 나온다. 값이 10, NULL, 20 이면 AVG 는 15 지 10 이 아니다.
  • COALESCE 위치가 두 컬럼에서 다르다.
    arpu — 분모(가입자 수)는 항상 1 이상이므로 분자를 0 으로 채운다: COALESCE(SUM(...), 0) / 가입자수
    arppu — 분모(결제 유저 수)가 0 일 수 있어 나눗셈 자체가 NULL 이 된다. 결과 전체를 0 으로 채운다: COALESCE(ROUND(...), 0)
    arppu 를 arpu 처럼 쓰면 결제 없는 채널에서 0 대신 NULL 이 나온다.
  • * 1.0 을 빼면 안 된다. amount 와 COUNT 가 둘 다 정수라 정수 나눗셈이 된다. 실제 토스 테스트에서 이걸로 틀린 적이 있다.
  • 정렬을 두 개 다 쓴다. arpu DESC 만 쓰면 동점에서 순서가 흔들린다.

이렇게 변형된다

“ARPPU 대신 중앙값”이면 ROW_NUMBER + COUNT() OVER 패턴. “월별 ARPU 추이”면 GROUP BY 월, 채널 로 바꾸되 분모를 그 달의 활성 유저로 둘지 전체 가입자로 둘지를 문제에서 확인하라 — 여기서 정의가 갈린다.

Q22. 한 번도 결제하지 않은 유저 수쉬움

쉬운 설명

명단에서 '숙제 안 낸 사람' 찾기. 쉬워 보이는데 함정이 하나 있고, 그것만 보는 문제다.

이게 함정이다.

SELECT 5 WHERE 5 NOT IN (1, 2, NULL) 0행

왜 그런가 — 이 식은 이렇게 풀린다.
5≠1(참) 그리고 5≠2(참) 그리고 5≠NULL(모름)
마지막을 모르니까 전체가 '모름' 이 되고, 조건에서 '모름' 은 거짓 취급이라 전부 탈락한다. 한 줄도 안 나온다.

이렇게 푼다

  1. 방법 1 — NOT EXISTS (SELECT 1 FROM payments p WHERE p.user_id = u.user_id)
  2. 방법 2 — 결제자 목록을 왼쪽 붙이기 하고 안 붙은 것만 센다 (p.user_id IS NULL).
  3. 채널별로 SUM(CASE WHEN p.user_id IS NULL THEN 1 ELSE 0 END).

이것만 피하면 된다

  • NOT IN 에 빈칸이 하나라도 섞이면 결과가 전부 사라진다. 본 데이터에는 빈칸이 없어서 통과하고, 다른 데이터셋에서 터진다. 실제 시험이 데이터셋을 여러 개 쓰는 이유가 이것이다.
  • NOT EXISTS 는 이 문제에 안전하다. 빈칸인 줄은 '같다' 비교가 성립하지 않아서 알아서 무시된다. '없는 것 찾기' 는 NOT EXISTS 를 기본으로 삼아라.
  • IN 은 괜찮다. 하나만 맞으면 참이니까. 부정형만 문제다.
  • COUNT(*) 로 세면 그 채널 전체 인원이 나온다. SUM(CASE WHEN … IS NULL THEN 1 ELSE 0 END) 이 맞다.
자세한 설명
묻는 것 · '존재하지 않는 것 찾기'. 쉬워 보이지만 NOT IN 을 쓰면 데이터에 NULL 이 하나 섞인 순간 결과가 0행이 된다. 이 함정 하나만 아는지 보는 문제다.

풀이 순서

  1. 결제한 유저 목록을 만든다. user_id 가 NULL 인 행은 뺀다 (누구의 결제인지 모르는 행이므로).
  2. users LEFT JOIN 그 목록 → 붙지 않은 유저가 '결제 없음' 이다.
  3. SUM(CASE WHEN p.user_id IS NULL THEN 1 ELSE 0 END) 으로 센다. COUNT(*) 로 세면 전체 유저 수가 나온다.
  4. 0 명인 채널도 한 행 나와야 하므로 WHERE 로 걸러내지 말고 CASE 로 센다.

정답 (MySQL)

-- 방법 1. LEFT JOIN ... IS NULL (0명인 채널도 행이 남는다)
SELECT u.channel,
       SUM(CASE WHEN p.user_id IS NULL THEN 1 ELSE 0 END) AS never_paid
FROM users u
LEFT JOIN (SELECT DISTINCT user_id FROM payments WHERE user_id IS NOT NULL) p
       ON p.user_id = u.user_id
GROUP BY u.channel
ORDER BY never_paid DESC, u.channel ASC;

-- 방법 2. NOT EXISTS — NULL 에 면역이라 IS NOT NULL 을 안 써도 된다
SELECT u.channel,
       SUM(CASE WHEN NOT EXISTS (SELECT 1 FROM payments p
                                  WHERE p.user_id = u.user_id)
                THEN 1 ELSE 0 END) AS never_paid
FROM users u
GROUP BY u.channel
ORDER BY never_paid DESC, u.channel ASC;

함정

  • NOT IN + NULL = 결과 전멸. 이게 이 문제의 핵심이다.
    WHERE u.user_id NOT IN (SELECT user_id FROM payments) 는 payments 에 NULL 이 한 행이라도 있으면 0행을 돌려준다.
    5 NOT IN (1, 2, NULL) 은 5<>1 AND 5<>2 AND 5<>NULL 이고, 마지막 항이 NULL 이라 전체가 NULL → WHERE 에서 거짓 취급 → 전부 탈락.
    본 데이터에는 NULL 이 없어서 통과하고, 「NULL섞임」 데이터셋에서 터진다. 실제 시험이 여러 데이터셋으로 채점하는 이유가 바로 이것이다.
  • NOT EXISTS 는 NULL 에 면역이다. p.user_id = u.user_id 가 NULL 이면 매칭 실패로 처리되어 그 행은 조용히 무시된다. '존재하지 않는 것 찾기' 는 NOT EXISTS 를 기본값으로 삼으면 이 사고가 안 난다.
  • IN 은 멀쩡하다. 하나만 맞으면 참이므로 NULL 이 섞여도 된다. 문제는 부정형(NOT IN)뿐이다.
  • COUNT(*) 로 세면 안 된다. LEFT JOIN 후 COUNT(*) 는 그 채널의 전체 유저 수다. SUM(CASE WHEN ... IS NULL THEN 1 ELSE 0 END) 이 정확하다.
  • 서브쿼리에 DISTINCT 를 넣어라. 안 넣으면 한 유저의 결제가 여러 건일 때 LEFT JOIN 으로 행이 불어난다. 여기서는 IS NULL 만 세니 결과가 같지만, 금액을 같이 구하는 변형에서 바로 깨진다.

이렇게 변형된다

“이탈 유저 찾기”, “한 번도 로그인 안 한 유저”, “재구매 없는 유저” 전부 같은 패턴. 반대로 “결제한 유저만”이면 EXISTS 또는 INNER JOIN + DISTINCT.

Q23. 유저별 결제 요약 (NULL 표시와 정렬 분리)보통

쉬운 설명

성적표에 '미응시' 라고 써 넣는 것은 된다. 그런데 그걸로 줄을 세우면 망한다.

COALESCE(날짜, '없음') 을 쓰면 날짜 칸이 글자 칸으로 바뀐다. 그걸로 줄을 세우면 사전순이 된다.

원래 (날짜)글자로 바꾸면
2026-01-05'2026-01-05'
2026-01-20'2026-01-20'
(빈칸)'없음' ← 글자라서 날짜들보다 뒤로 간다

숫자에서도 똑같다. 글자로 바뀌면 '9' 가 '20' 보다 크다. 사전순이니까 첫 글자 9 와 2 를 비교하는 것이다.

이렇게 푼다

  1. 유저 명단 왼쪽에 두고 결제를 붙여서 합계·첫 결제일·마지막 결제일을 만든다.
  2. 금액은 COALESCE(SUM(금액), 0) — SUM 밖에 씌운다.
  3. 첫 결제일은 빈칸 그대로 둔다. 글자로 바꾸지 않는다.
  4. 플랜 이름은 원래 글자라서 COALESCE(…, '없음') 이 안전하다.
  5. 줄 세우기는 원래 칸으로 한다.

이것만 피하면 된다

  • MySQL 은 이 변환을 에러 없이 조용히 해 버린다. 빨간 줄도 안 뜨고, 결과만 틀린다. 그래서 더 위험하다.
  • 보여줄 값과 줄 세울 값을 분리해라. 글자로 보여주고 싶으면 그 칸은 따로 만들고, ORDER BY 에는 원래 칸을 쓴다.
  • 빈칸의 줄 세우기 위치: MySQL·SQLite 는 빈칸을 가장 작은 값으로 본다 → 오름차순이면 맨 앞. 확실하게 하려면 ORDER BY (칸 IS NULL), 칸 으로 직접 정해라.
  • 마지막 플랜을 MAX(plan) 로 뽑으면 틀린다. 그건 알파벳 순으로 가장 큰 글자다 ('pro' > 'basic'). '마지막' 은 날짜로 찾아야 한다.
자세한 설명
묻는 것 · 토스 쿼리 테스트에 나온 '데이터 타입 문제' 가 정확히 이 유형이다. 보여 줄 값과 정렬할 값을 분리할 수 있는지를 본다.

풀이 순서

  1. users LEFT JOIN payments + GROUP BY user_id 로 유저별 합계·첫 결제일·마지막 결제일을 만든다.
  2. 금액은 COALESCE(SUM(p.amount), 0) — SUM 밖에 씌운다.
  3. 첫 결제일은 NULL 을 그대로 둔다. 문자열로 바꾸면 정렬이 깨진다.
  4. 마지막 plan 은 paid_date = MAX(paid_date) 로 다시 조인해 가져오고 COALESCE(..., '없음') — 이 컬럼은 원래 문자열이라 안전하다.
  5. 정렬은 원본 컬럼으로 한다: ORDER BY total_amount DESC, first_paid ASC, user_id ASC.

정답 (MySQL)

WITH s AS (
  SELECT u.user_id,
         COALESCE(SUM(p.amount), 0) AS total_amount,
         MIN(p.paid_date)           AS first_paid,
         MAX(p.paid_date)           AS last_paid
  FROM users u
  LEFT JOIN payments p ON p.user_id = u.user_id
  GROUP BY u.user_id
)
SELECT s.user_id, s.total_amount, s.first_paid,
       COALESCE(MAX(lp.plan), '없음') AS plan_label
FROM s
LEFT JOIN payments lp
       ON lp.user_id = s.user_id AND lp.paid_date = s.last_paid
GROUP BY s.user_id, s.total_amount, s.first_paid
ORDER BY s.total_amount DESC, s.first_paid ASC, s.user_id ASC
LIMIT 20;

함정

  • 날짜에 COALESCE 로 문자열을 넣으면 컬럼 전체가 문자열이 된다. COALESCE(first_paid, '없음') 을 쓰면 반환 타입이 공통 타입인 문자열로 승격되고, 그걸로 정렬하면 사전순이 된다. MySQL·SQLite 는 이 변환을 오류 없이 조용히 하므로 에러도 안 나고 결과만 틀린다. (PostgreSQL·DuckDB 는 오류를 낸다.)
    해법: 표시와 정렬을 분리한다. 표시용 문자열 컬럼을 따로 만들고 ORDER BY 에는 원본 컬럼을 쓴다.
  • 정렬에서 NULL 의 위치는 엔진마다 다르다. 실제로 돌려 본 결과:
    MySQL·SQLite → NULL 을 가장 작은 값으로 본다 (ASC 면 맨 앞, DESC 면 맨 뒤)
    PostgreSQL·DuckDB → 기본이 NULLS LAST (ASC 에서도 맨 뒤)
    확실하게 하려면 ORDER BY (first_paid IS NULL), first_paid 처럼 IS NULL(0/1)을 첫 키로 써서 직접 정한다. MySQL 에는 NULLS LAST 문법이 없다.
  • COALESCE 를 SUM 안에 넣을지 밖에 씌울지. LEFT JOIN + GROUP BY 왼쪽테이블 이면 그룹마다 NULL 행이 한 개 남아 SUM(COALESCE(amount,0)) 도 0 이 나온다. 하지만 그룹 자체가 비는 경우(상관 서브쿼리, INNER JOIN 뒤)는 SUM 이 NULL 이고 안쪽 COALESCE 는 실행될 기회가 없다. 밖에 씌우는 쪽이 항상 안전하다.
  • 마지막 plan 을 MAX(plan) 로 바로 뽑으면 틀린다. 그건 '알파벳 순으로 가장 큰 plan' 이다 ('pro' > 'basic'). '마지막 결제의 plan' 은 날짜로 찾아야 한다 — paid_date = MAX(paid_date) 로 재조인하거나 ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY paid_date DESC) 로 1 번만 남긴다.
  • LIMIT 은 정렬 뒤에 걸린다. ORDER BY 를 빼고 LIMIT 만 쓰면 아무 20행이 나온다. 20번째와 21번째가 완전 동점이면 어느 쪽이 들어올지 정해지지 않으므로, 문제가 준 정렬 키를 전부 써야 한다.

이렇게 변형된다

“결제 없는 유저를 맨 뒤로”면 ORDER BY (first_paid IS NULL), first_paid. “마지막 결제 금액까지”면 재조인에서 MAX(lp.amount) 를 같이 가져온다. “N일 이상 결제 없는 유저”면 DATEDIFF(기준일, MAX(paid_date)) >= N 에 MAX(paid_date) IS NULL 케이스를 따로 처리한다.
